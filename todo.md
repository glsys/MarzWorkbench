# Editable MarzWorkbench — implementation plan and handover

> **Goal:** Marz creates a complete guitar as a **native, parametric FreeCAD model**. The user subsequently refines **any** generated component in FreeCAD's normal workbenches. Ordinary **Recompute** follows links and **never restores Marz defaults**. Explicit **Regenerate [component]** replaces that component's manually edited construction from current Marz parameters; loss of those edits is intentional and expected.
>

## 2. Non-negotiable model semantics

- **Create:** Marz instantiates meaningful, persistent FreeCAD objects with editable properties, native icons and correct source links.
- **Refine:** User may edit splines/control points, Draft wires, dimensions, placements, cut profiles, feature parameters, etc. using established FreeCAD/Curves/Draft/Part editors. Avoid custom XYZ pole-list editing when an existing FreeCAD editor is capable.
- **Recompute:** FreeCAD recomputes derived objects via native dependencies (`Base`, `Profile`, `Source`, `App::PropertyLink[/List]`, etc. as appropriate); do not regenerate/edit source objects behind the user's back. Handle restore and recompute after document reopening.
- **Regenerate [component]:** Explicit destructive reset **only** for that component's Marz-generated source/construction objects. Recompute final dependent output, possibly in *other* components, without resetting their authored inputs. Keep a distinct **Regenerate All** action.
- **Regenerate Headstock:** Separate from the neck if the geometry dependencies permit it; changes may recompute finished neck but may not regenerate neck profiles/guides. Headstock creation and neck/headstock fusion are separate stages.
- **Reimport SVG:** Separate action from ordinary recompute and from regeneration of an unrelated component. Reimport may replace only the relevant imported geometry, with clear indication that manual edits to it will be lost.
- **No opaque copies as model inputs:** Do not link a parametric result to a one-time `.Shape.copy()` when a persistent editable source exists. A shape copy is fine *inside an execute operation*; it is not a dependency graph.
- **No fictitious native type:** Choose a real FreeCAD feature that represents the geometry. `Part::Feature` is acceptable only for irreducible terminal/intermediate shapes whose inputs are still editable and linked. Use stock view providers rather than assigning `.Proxy` to native `PartGui.ViewProviderPartExt` (this previously caused a runtime crash).
- **Geometric fidelity:** Before any manual edits, the new generated geometry should match the existing generator (including transforms, contour orientation, trimming and cutting side). If a different FreeCAD implementation yields a different shape, investigate before replacing the algorithm. Report unsupported geometry honestly; no silent omissions.
- **Visibility:** Start construction hidden if useful, but user must be able to show it with the eye icon. Do not forcibly hide it on every recompute/update or reset user-chosen visibility.
- **Compatibility:** Preserve meaningful object names/links where possible, avoid breaking external references; migrate saved documents without discarding edited shapes. Explicitly distinguish a generated object from a modified one if needed for safe migration.

### Planned master-sketch / native-operation architecture

The intended end state is **not "one Sketcher object merely because the geometry came from one SVG file"**. The intended design is the FreeCAD **master-sketch** pattern: one authoritative Sketcher object for geometry that belongs to the same physical drawing plane / construction context, and downstream native operations select only the closed regions they need.

For FreeCAD 1.1+, the Body migration now uses the master sketch's authored semantic edge loops through native profile binders. The `MakeInternals` / `InternalFaceN` approach was tested in 0.2.9-0.2.12 and rejected because overlapping/crossing loops did not yield stable selectable partitions in FreeCAD 1.1.4. Continue the edge-loop binder architecture against the 0.1.66 geometry/placement baseline.

For the body, the target architecture is conceptually:

```text
Body Master Sketch
  outer contour
  bridge / construction references
  pocket A
  pocket B
  pocket C
  ...

Body Top (native feature history)
  Pad / blank              <- outer-contour internal face
  Pocket start=0 end=5     <- faces A, C, ...
  Pocket start=0 end=20    <- faces B, ...
  Pocket start=5 end=20    <- ...
  ergonomic / neck cuts

Body Back (native feature history)
  reversed Pad / blank     <- same master-interface profile, grows toward Back
  Pocket ...
```

The **master sketch owns geometry**. The **operation owns machining semantics**. Pockets that share one operation are grouped by **`(target, start, end)`**, where target is Both / Top / Back and `end = start + depth` under the current Marz metadata convention. A native operation should reference all matching semantic closed loops from the one Body Master at once; do not create a separate sketch merely to group equal-depth pockets. `InternalFaceN` was tested and rejected because overlapping/crossing loops do not produce stable partitions in FreeCAD 1.1.4; use a native profile adapter/binder over the authored master edges instead.

`Both` means the same source regions participate in the appropriate operation history of both body halves; Top-only and Back-only groups exist only in their respective histories. Preserve the current Marz start/end interpretation until its coordinate/direction semantics are verified against existing output. Prefer storing Start/End (or the equivalent native parameters) on the operation, not redundantly on every profile. If a stock Part Design Pocket cannot directly express a nonzero start plane, use an explicit datum/offset/reference or another native subtractive feature while keeping the same master-sketch source.

SVG IDs remain important for import, regeneration and semantic identity, but **do not persistently identify operations by `FaceN` numbers**. Keep the stable SVG-ID/geometry-index map and rebuild each native profile binder from the corresponding authored master edges when explicitly regenerating or reimporting. Ordinary FreeCAD Recompute must follow existing links without silently reimporting or regrouping user geometry; explicit SVG reimport / component regeneration is the destructive reset boundary.

The planned **Headstock Master Sketch** follows the same rule with one important distinction: its transition line is real, non-construction geometry because it partitions the custom contour into the neck-side region and the actual plate region. The native headstock Pad consumes only internal faces on the plate side; SVG pockets are grouped by `(start, end)` and applied as native Part Design Pockets. The top-transition and volute cutters are separate geometric operations and must not be folded into the SVG-pocket grouping merely because they also remove material.

The **body neck-pocket outline** is also intended to move into the Body Master Sketch as a special semantic region with the exact SVG ID **`neckpocket`**. It is not an ordinary `(target,start,end)` pocket group: its machining depth/start semantics come from the neck-pocket/body parameters, while the profile comes from the master sketch. The `neckpocket` closed profile is explicitly allowed to extend partly outside the body outer contour and may cross/protrude beyond that contour; import, validation and internal-face/profile resolution must therefore **not clip it, reject it for being outside, or require containment inside the body outline**. Its native subtractive operation must use the body/master construction plane so the cutter direction is normal (90°) to that plane. If overlapping master-sketch loops make a single `InternalFaceN` unstable or split, resolve the `neckpocket` geometry by its semantic SVG-ID/geometry indices and feed the complete closed profile through a binder/profile adapter rather than changing or clipping the user geometry. Initially, absence of `neckpocket` should retain the current generated neck-pocket cutter as a fallback; presence of `neckpocket` makes the user-authored profile authoritative.

As of 0.2.4, ordinary Body SVG pockets are cut from `Marz_Sketch_BodyMaster`; the older `Marz_Sketch_BodyPockets` remains only an import/fallback source. The pocket-properties dock prefers the Body Master and updates its semantic map/operation grouping. Native Start/End operation properties should eventually become the authoritative machining parameters; the dock can then disappear or become only a convenience UI over those native properties.

### F1. Inlay SVG logical groups and two-axis parametric placement

Target: preserve the existing ability to build one logical fretboard inlay from **multiple individually tagged SVG elements**, and additionally allow an SVG `<g>` to define that same logical unit more conveniently. Fret assignment and placement come from a shared **semantic designation prefix**; arbitrary trailing text exists only to keep XML/SVG IDs unique. Placement must remain parametric so scale length, multiscale/fret positions and fretboard width changes move the inlay without rewriting its Sketcher geometry.

> **Flexible SVG naming syntax (future parser requirement):** `p` is the preferred ID-safe decimal separator and `a`/`s` are preferred ID-safe signed-offset markers, but **the parser must accept both encodings in both `id` and `inkscape:label`**. `p`, `P`, and `.` are equivalent; `a`, `A`, and `+` are equivalent; `s`, `S`, and `-` are equivalent. Match `f/F`, `x/X`, and `y/Y` case-insensitively. The human-readable compact legacy form `D13X0.25+2Y1.0-2.5` must also be accepted regardless of whether it appears in `id` or `label` (including `d/D` as a legacy inlay prefix). Prefer a matching `id`; check `inkscape:label` only if the `id` does not match. Do not introduce separate grammar rules for labels versus IDs.

#### SVG semantic designation, grouping, and optional `<g>` form

- [ ] Preserve both authoring forms:
  - **Individually tagged elements:** paths/circles/etc. with the same parsed fret + X/Y placement prefix form **one logical inlay**, even when arbitrary suffixes distinguish them, e.g. `f13_x0a2p5_y1s2p5_part1` and `f13_x0a2p5_y1s2p5_part2`. The suffix (`part1`, `part2`, `circle`, etc.) has no placement meaning; retain complete source IDs for reimport/diagnostics.
  - **Tagged SVG `<g>` group:** a valid designation on the group ID/label groups its supported closed descendants into one logical inlay; children need not repeat semantic names. Different tagged groups remain distinct logical inlays even with identical positions. This must coexist with individually tagged elements.
- [ ] Use the **inlay** designation `f<N>` or `f<N>_` (centered by default), optionally followed by underscore-separated `x<V>[a<mm>|s<mm>]` and/or `y<V>[a<mm>|s<mm>]` tokens and arbitrary descriptive/uniqueness tokens. `N` is an integer fret-space number, `V` is a normalized alignment value from 0 to 1, and offsets are in millimetres. **Underscores delimit tokens: inspect and parse each complete token separately**, regardless of X/Y token order; do not use one prefix regex that consumes or rejects everything after the first match. A final underscore (empty token) is allowed, as is no underscore after a bare fret designation. A token that does not match a complete recognized modifier (e.g. `apple` or `xaviar`) is a free-text suffix, not an invalid X modifier. Also accept the equivalent legacy compact form, e.g. `D13X0.25+2Y1.0-2.5`, with its X/Y fields parsed within that single token. Apply the case-insensitive decimal/sign variants from the rule above in **both** IDs and labels.
- [ ] **Default centered placement:** unmodified `f13` and `f13_` are centered longitudinally **between fret 12 and fret 13** and laterally across the fretboard. This is **verified in current code**: `fretPos(13, ...)` uses the midpoint of `fret(12)` and `fret(13)` and the imported compound is recentered to its own bounding-box center. `f13_x0p5a0p0_y0p5a0p0` and equivalent punctuation/case variants must produce the same placement; the earlier `y0.5` spelling was a typo in the canonical ID example, **not** a separate label-only syntax.
- [ ] **Box-aligned axes, not per-element point offsets:** compute placement using the **complete logical inlay's bounding box** and its available movement within fret space `N`. For X, `x0` aligns the left/nut-side box edge with fret `N-1`; `x1` aligns the right/bridge-side box edge with fret `N`; `x0p25` positions the box at one-quarter of the normalized available travel between those boundaries; `x0p5` centers it. For Y, apply the same rule from the treble-side (`y0`) to bass-side (`y1`) usable fretboard edges, keeping the whole box within bounds (including taper/multiscale). **Examples:** `f13_x0`, `f13_x1`, and `f13_x0p25` all refer to fret space 12–13. The exact quarter-point reference is box-aligned, rather than placing each geometric control point at 25% of the raw interval.
- [ ] **Signed physical padding:** `a` adds a positive millimetre displacement, `s` subtracts it, after normalized box alignment. In fret space 12–13, `f13_x0a2p5` starts 2.5 mm inward from fret 12; `f13_x1s2p5` finishes 2.5 mm inward from fret 13. Y follows the same convention: `y0a2p5` moves inward from the treble edge and `y1s2p5` inward from the bass edge. Mixed alignment and padding such as `f13_x0p5a2p5_y1s2p5` is valid. Missing offsets mean 0 mm; missing axes mean `0p5`.
- [ ] **Parsing examples that must all be accepted** (the last token may be arbitrary text or empty): `f12_x0p0a0_y0p0a0p0_apple`, `f12_y0p0a0p0_x0p0a0_xaviar`, `f12_y0p0a0p0_x0p0a0_`, `f12_y0p0a0p0_x0p0a0`, `f12_y0p0a0p0_`, `f12_y0p0a0p0`, `f12_`, and `f12`. The `xaviar` suffix must **not** be interpreted as a malformed `x` token; the X and Y fields may appear in either order. Recognize semantic modifiers only when the entire underscore-delimited token has their valid numeric grammar.
- [ ] Reject or report genuinely malformed/contradictory semantic modifiers in the Inlay results **Validation** column, without guessing an alternate placement; **do not** reject an otherwise valid designation for unrelated free-text suffix tokens or trailing `_`. Preserve existing centered inlays when placement modifiers are absent. Keep first-valid `id` / fallback `inkscape:label` behavior consistent for standalone and group elements.

#### FreeCAD representation

- [ ] Create **one editable `Sketcher::SketchObject` per logical SVG inlay**, whether that inlay came from a tagged `<g>` or from multiple individually tagged elements sharing one semantic designation. Do not create one sketch merely per fret number or one sketch per SVG child. Preserve every child curve/loop as native Sketcher geometry where possible while retaining their relative positions inside the group. A multi-part logo/inlay therefore edits as one sketch and moves as one unit.
- [ ] Keep the sketch geometry in a stable **local inlay coordinate system**. Do not bake fret placement, normalized alignment or millimetre padding destructively into every control point. The visible sketch's document placement/attachment (or a dedicated native placement adapter if required) is derived from the semantic placement properties, so changing fret positions or alignment moves the whole sketch without altering its authored shape.
- [ ] Expose the parsed placement semantics as explicit Data properties on the inlay sketch (or its directly owning semantic object if FreeCAD requires a placement proxy): at minimum `Fret`, `AlignX`, `AlignY`, `OffsetX`, `OffsetY`, and stable `SVGInlayID` plus original source/group IDs. The values must be inspectable/editable in FreeCAD and must agree with the imported semantic designation metadata. Reimport resets these values from SVG; ordinary recompute follows the current properties and must not silently rewrite edited geometry.
- [ ] Make the **displayed sketch appear at its actual fretboard plan position**, even though its geometry remains local. A user editing the sketch should see the inlay where it will be cut. Placement recomputation derives X from the current fret-space boundaries and the group's longitudinal bounds, and derives Y from the current usable fretboard edges at the placed inlay extent. For tapered/multiscale fretboards, lateral alignment must keep the **complete inlay group** inside the intended usable outline; do not assume one constant fretboard width measured at a single X if the inlay spans a significant longitudinal distance.
- [ ] Separate semantic placement from the actual fretboard-surface/cutter construction. The editable sketch owns 2D shape + fret/alignment/offset metadata; linked binder/attachment/native Pocket machinery may project/position that shape onto the compound-radius fretboard and apply `fretboard.inlayDepth`. Do not encode inlay depth in the SVG group grammar unless a later design explicitly adds per-inlay depth.
- [ ] Implement semantic SVG/XML parsing, optional tagged groups, standalone suffix grouping, per-logical-inlay Sketcher sources, editable placement properties, two-axis cell-aware placement and signed millimetre padding using the token-by-token case-insensitive, punctuation-tolerant grammar specified above (including the compact legacy variant). Keep the current fretboard cutter until the broader fretboard-native refactor is ready.
- [ ] Add regression coverage for: centered legacy equivalence; all eight token/suffix examples above; reversed X/Y token order; trailing and absent underscores; mixed-case `F/X/Y/P/A/S` and `.`, `+`, `-` variants in **both** `id` and `label`; the compact `D13X0.25+2Y1.0-2.5` variant; full-token recognition (`xaviar` remains free text); two independent inlays in the same fret; multi-element group bounds; `x0a2p5`/`x1s2p5` and corresponding Y edge padding; scale-length/fret-position changes; tapered/multiscale lateral limits; save/reopen; editable sketch geometry surviving ordinary recompute; and explicit Inlay SVG reimport restoring the SVG-authored semantic metadata; standalone elements with the same semantic prefix but different trailing uniqueness suffixes grouping into one sketch; and a tagged `<g>` producing the equivalent one-sketch result. Rebuild the discarded experiment's parser/grouping coverage against the revised grammar; actual FreeCAD save/reopen, scale-change recompute and SVG reimport behavior require GUI/runtime verification.

#### Fractional-fret placement

- [ ] Interpret every neck section position in **fret coordinates**, not millimetres. `0.0` is the nut/fret 0, `5.0` is exactly at fret 5, and `0.33` is one third of the physical distance from fret 0 to fret 1. For `p = n + f`, place the section along the same neck/fret reference axis used by Marz at `x(p) = x(n) + f * (x(n+1) - x(n))`. This keeps sections attached to the musical fret layout when scale length or multiscale geometry changes.
- [ ] Each imported section becomes an editable transverse FreeCAD curve/sketch on its own physical section plane. One SVG may define the whole family, but **do not force all sections into one master sketch** because the sections intentionally live on different planes. Normalize section orientation (treble edge -> bass edge, or the inverse chosen once and documented) before building correspondence.

#### Smooth Gordon/curve-network interpolation without fixed dense resampling

- [ ] Replace the current blanket preprocessing that discretizes every generated neck profile to **100 points** before rebuilding it as a B-spline. SVG section curves may contain different native primitives/pole counts; keep the authored section curve itself as the profile wherever the surface API permits. The Gordon/guide construction needs corresponding locations across profiles, **not identical original SVG point counts**.
- [ ] Generate longitudinal guide curves from common **normalized lateral neck-width stations** `u in [0,1]`, rather than matching B-spline pole indices or normalized curve arc length. `u=0` and `u=1` are the two neck edges and `u=0.5` is the physical centerline. For each transverse section, evaluate/intersect the exact section curve at the same lateral station so every guide has a physically meaningful correspondence across changing neck widths and profile shapes.
- [ ] Start with a small mandatory station set (conceptually `0, 0.25, 0.5, 0.75, 1`) and **adaptively refine** it. Insert additional lateral stations only where curvature/profile differences or reconstructed-surface error between existing stations exceeds a defined tolerance. Stop when the tolerance is met or a configurable safety cap is reached. Benchmark/tune the initial tolerance and cap against real guitars rather than hard-coding a large point count; the intended range is a small guide network (roughly single-digit to low-double-digit guides), not 100 longitudinal guides.
- [ ] Preserve smooth longitudinal transitions through all supplied fractional-fret sections using the existing Gordon-style surface machinery or an equivalent curve-network surface. Reparameterize/fit only as much as that surface implementation actually requires. Validate that the surface passes through the supplied section profiles and that adaptive-guide refinement converges without visible flats, kinks or shoulder drift.
- [ ] Add performance and geometry regression measurements against the current C/D path: surface construction time, number of transverse sections, number of generated longitudinal guides, shape validity, representative section deviations and resulting neck bounds. The SVG path should not make the already-expensive Gordon stage substantially slower merely because an input curve has many original SVG control points.

## 6. Historical failures and lessons — do not repeat

1. The first neck refactor exposed generic `Part::FeaturePython` poles and `Part::Feature` cutters. This produced wrong generic icons, incomplete interactive editing and visibility/view-provider problems. Adding `.Proxy` to native `PartGui.ViewProviderPartExt` crashed in FreeCAD; use proper native feature types.
2. A heel plane was copied using a source face's identity `Placement`; the source geometry contained its world offset, so the new native plane ended up at the origin. Fixes must verify **world-space BREP**, not merely local Placement. FreeCAD quantities (`obj.Length`, `obj.Width`) must be compared via numeric `.Value` to unitless `BoundBox` floats.
3. Headstock fuse yielded an empty solid; repeated fuzzy-tolerance/repair attempts did not solve a wrong upstream geometry. Diagnostics showed the old and editable curve networks, Gordon surface, heel plane and trimmed blank became identical. **Fix the first divergent stage rather than add Boolean workarounds.**
4. The newer uploaded guitar exhibited an **inverted neck blank** (negative signed volume). Patch `0011` (`0.1.34`) corrects orientation before heel slicing; a focused test using saved BREP produced two heel-cut solids and a valid neck/headstock fusion. **This was not yet confirmed as passing in the user's full FreeCAD GUI** at handover.
5. The original March-era test document and newly reimported SVG document gave different results even on unmodified Marz master; imported shapes are persisted in the document and not necessarily recreated by **Update Parts**. Do not attribute every mismatch to Marz parameters or to the latest branch.
6. Mock and syntax tests did not catch runtime FreeCAD `Quantity` unit errors, missing view-provider properties or OCC errors. For future patches, prefer actual FreeCAD tests on the provided documents; record honestly when running FreeCAD is impossible.
7. The 0.1.36 SVG-to-Sketch pilot uses `Draft.make_sketch` on the *already transformed and anchored* native wire. A saved sketch overrides its legacy `Marz_*` source in existing consumers, but the terminal body/neck/headstock generators still write finished shapes, so **ordinary FreeCAD Recompute alone is not yet sufficient** to rebuild those assemblies; **Update Parts** consumes changed sketch geometry. Reimporting an SVG deletes only its corresponding editable sketches, intentionally discarding their edits. The menu conversion command does not overwrite a preexisting sketch. Version 0.1.62 supersedes the 0.1.44 single-spline contour representation: straight spans stay native lines and cubic spans stay exact B-spline segments, joined by Coincident constraints (requires explicit reimport for existing sketches). Version 0.1.37 accepts harmless segment reordering/reversal during initial validation, but initial finished-model equivalence and post-edit wire orientation still require GUI verification; if winding changes model results, normalize downstream construction without losing edits.
8. A successful OCC Boolean may normalize or bake a shape's `Placement`; do not depend on `Shape.Placement` surviving `cut()` for later body positioning. Keep the native Body extrusion in its final frame and transform SVG-local cutters into that frame before subtraction. Patch 0051 applies this to ordinary Body Master pockets and semantic `neckpocket`, matching the planned native Part/Part Design cut ownership.
9. **Native migration must purge the old object graph before creating replacements.** The full 0.2.22 FreeCAD tree dump showed `Marz_Body_Top` / `Marz_Body_Back` were still legacy `Part::FeaturePython` objects, with old `Part::Extrusion` blanks, contour `App::Link`s, construction groups and derived cutter features attached. Protecting those canonical-name legacy objects during cleanup directly caused `Body Top001` / `Body Back001`. For Headstock and later components, inventory exact internal names/types first, delete owned children before containers, purge the legacy graph, then create one persistent native container and rebuild only its owned history on subsequent updates. Do not diagnose migration from display labels alone.
