# Editable MarzWorkbench — implementation plan and handover

> **Goal:** Marz creates a complete guitar as a **native, parametric FreeCAD model**. The user subsequently refines **any** generated component in FreeCAD's normal workbenches. Ordinary **Recompute** follows links and **never restores Marz defaults**. Explicit **Regenerate [component]** replaces that component's manually edited construction from current Marz parameters; loss of those edits is intentional and expected.
>
> This is the implementation checklist, design contract, and continuity record for another chat. Update checkboxes **in the patch that completes each task**. Record verified behavior here, not guesses. `devops.md` is authoritative for commits, versioning, and patch delivery.

## 2. Non-negotiable model semantics

- **Create:** Marz instantiates meaningful, persistent FreeCAD objects with editable properties, native icons and correct source links.
- **Refine:** User may edit splines/control points, Draft wires, dimensions, placements, cut profiles, feature parameters, etc. using established FreeCAD/Curves/Draft/Part editors. Avoid custom XYZ pole-list editing when an existing FreeCAD editor is capable.
- **Recompute:** FreeCAD recomputes derived objects via native dependencies (`Base`, `Profile`, `Source`, `App::PropertyLink[/List]`, etc. as appropriate); do not regenerate/edit source objects behind the user's back. Handle restore and recompute after document reopening.
- **Regenerate [component]:** Explicit destructive reset **only** for that component's Marz-generated source/construction objects. Recompute final dependent output, possibly in *other* components, without resetting their authored inputs. Keep a distinct **Regenerate All** action.
- **Regenerate Headstock:** Separate from the neck if the geometry dependencies permit it; changes may recompute finished neck but may not regenerate neck profiles/guides. Headstock creation and neck/headstock fusion are separate stages.
- **Reimport SVG:** Separate action from ordinary recompute and from regeneration of an unrelated component. Reimport may replace only the relevant imported geometry, with clear indication that manual edits to it will be lost.
- **No opaque copies as model inputs:** Do not link a parametric result to a one-time `.Shape.copy()` when a persistent editable source exists. A shape copy is fine *inside an execute operation*; it is not a dependency graph.
- **No fictitious native type:** Choose a real FreeCAD feature that represents the geometry. `Part::Feature` is acceptable only for irreducible terminal/intermediate shapes whose inputs are still editable and linked. Use stock view providers rather than assigning `.Proxy` to native `PartGui.ViewProviderPartExt` (this previously caused a runtime crash).
- **Geometric fidelity:** Before any manual edits, the new generated geometry should match the existing generator (including transforms, contour orientation, trimming and cutting side). If a different FreeCAD implementation yields a different shape, investigate before replacing the algorithm. Report unsupported geometry honestly; no silent omissions.
- **Visibility:** Start construction hidden if useful, but user must be able to show it with the eye icon. Do not forcibly hide it on every recompute/update or reset user-chosen visibility.
- **Compatibility:** Preserve meaningful object names/links where possible, avoid breaking external references; migrate saved documents without discarding edited shapes. Explicitly distinguish a generated object from a modified one if needed for safe migration.

### Planned master-sketch / native-operation architecture

The intended end state is **not "one Sketcher object merely because the geometry came from one SVG file"**. The intended design is the FreeCAD **master-sketch** pattern: one authoritative Sketcher object for geometry that belongs to the same physical drawing plane / construction context, and downstream native operations select only the closed regions they need.

For FreeCAD 1.1+, investigate and use Sketcher's **internal profile faces** (`MakeInternals`) so closed regions of one master sketch can be selected as subelements by Part Design features. The discarded 0.2.x experiment explored semantic re-resolution of `InternalFaceN` regions and body-local adapters, but that implementation was reverted and must not be treated as verified. Rebuild this incrementally against the 0.1.66 geometry/placement baseline.

For the body, the target architecture is conceptually:

```text
Body Master Sketch
  outer contour
  bridge / construction references
  pocket A
  pocket B
  pocket C
  ...

Body Top (native feature history)
  Pad / blank              <- outer-contour internal face
  Pocket start=0 end=5     <- faces A, C, ...
  Pocket start=0 end=20    <- faces B, ...
  Pocket start=5 end=20    <- ...
  ergonomic / neck cuts

Body Back (native feature history)
  reversed Pad / blank     <- same master-interface profile, grows toward Back
  Pocket ...
```

The **master sketch owns geometry**. The **operation owns machining semantics**. Pockets that share one operation are grouped by **`(target, start, end)`**, where target is Both / Top / Back and `end = start + depth` under the current Marz metadata convention. A native operation should reference all matching internal faces at once; do not create a separate sketch merely to group equal-depth pockets.

`Both` means the same source regions participate in the appropriate operation history of both body halves; Top-only and Back-only groups exist only in their respective histories. Preserve the current Marz start/end interpretation until its coordinate/direction semantics are verified against existing output. Prefer storing Start/End (or the equivalent native parameters) on the operation, not redundantly on every profile. If a stock Part Design Pocket cannot directly express a nonzero start plane, use an explicit datum/offset/reference or another native subtractive feature while keeping the same master-sketch source.

SVG IDs remain important for import, regeneration and semantic identity, but **do not persistently identify operations by `FaceN` numbers**. Internal-face numbering may change when the master sketch is edited. Keep a stable SVG-ID/geometry-region map and resolve the corresponding internal faces when building or regenerating native operations. Ordinary FreeCAD Recompute must follow existing links without silently reimporting or regrouping user geometry; explicit SVG reimport / component regeneration is the destructive reset boundary.

The planned **Headstock Master Sketch** follows the same rule with one important distinction: its transition line is real, non-construction geometry because it partitions the custom contour into the neck-side region and the actual plate region. The native headstock Pad consumes only internal faces on the plate side; SVG pockets are grouped by `(start, end)` and applied as native Part Design Pockets. The top-transition and volute cutters are separate geometric operations and must not be folded into the SVG-pocket grouping merely because they also remove material.

The **body neck-pocket outline** is also intended to move into the Body Master Sketch as a special semantic region with the exact SVG ID **`neckpocket`**. It is not an ordinary `(target,start,end)` pocket group: its machining depth/start semantics come from the neck-pocket/body parameters, while the profile comes from the master sketch. The `neckpocket` closed profile is explicitly allowed to extend partly outside the body outer contour and may cross/protrude beyond that contour; import, validation and internal-face/profile resolution must therefore **not clip it, reject it for being outside, or require containment inside the body outline**. Its native subtractive operation must use the body/master construction plane so the cutter direction is normal (90°) to that plane. If overlapping master-sketch loops make a single `InternalFaceN` unstable or split, resolve the `neckpocket` geometry by its semantic SVG-ID/geometry indices and feed the complete closed profile through a binder/profile adapter rather than changing or clipping the user geometry. Initially, absence of `neckpocket` should retain the current generated neck-pocket cutter as a fallback; presence of `neckpocket` makes the user-authored profile authoritative.

As of 0.2.4, ordinary Body SVG pockets are cut from `Marz_Sketch_BodyMaster`; the older `Marz_Sketch_BodyPockets` remains only an import/fallback source. The pocket-properties dock prefers the Body Master and updates its semantic map/operation grouping. Native Start/End operation properties should eventually become the authoritative machining parameters; the dock can then disappear or become only a convenience UI over those native properties.

### F1. Inlay SVG logical groups and two-axis parametric placement

Target: preserve the existing ability to build one logical fretboard inlay from **multiple individually tagged SVG elements**, and additionally allow an SVG `<g>` to define that same logical unit more conveniently. Fret assignment and placement come from a shared **semantic designation prefix**; arbitrary trailing text exists only to keep XML/SVG IDs unique. Placement must remain parametric so scale length, multiscale/fret positions and fretboard width changes move the inlay without rewriting its Sketcher geometry.

> **ID-format warning:** the discarded 0.2.x experiment showed that punctuation in SVG/XML IDs is not stable across the SVG/Inkscape/FreeCAD import chain. In particular, `.` and `-` must not be relied on, and `+` was observed being sanitized to `_`. Therefore the `ax0.5`, `ax0+2.5`, `ax1-2.5`, etc. examples below document the **semantic intent only**, not the final literal ID syntax. Before implementation, define an identifier-safe encoding using letters, digits and `_` only (for example separate sign/decimal tokens), while retaining human-readable values in FreeCAD properties/result tables.

#### SVG semantic designation and optional `<g>` form

- [ ] Keep both authoring forms valid:
  - **Individually tagged elements:** paths/circles/etc. whose IDs/labels share the same parsed semantic prefix are collected into one logical inlay. Their literal SVG IDs remain unique by carrying arbitrary trailing suffixes, e.g. `f12_ax1-2.5_ay0.5_part1`, `f12_ax1-2.5_ay0.5_part2`, `f12_ax1-2.5_ay0.5_circle`. All three parse to semantic designation `f12_ax1-2.5_ay0.5` and therefore become one inlay sketch.
  - **Tagged SVG group:** a `<g>` whose ID/label contains the semantic designation defines one logical inlay from all supported closed child geometry. Child IDs are then ordinary SVG/Inkscape uniqueness data and do not carry placement semantics. This is an additional convenience form, **not a replacement** for individually tagged elements. Separate tagged groups remain separate logical inlays even if they happen to have identical fret/alignment metadata.
- [ ] Parse the semantic designation only from the recognized leading tokens: `f<N>` plus optional `ax<V>[+/-mm]` and `ay<V>[+/-mm]`. Once those recognized tokens end, treat the remaining `_...` suffix as arbitrary uniqueness/descriptive text and **exclude it from grouping and placement semantics**. Do not require suffixes to follow names such as `part1`; `_part1`, `_part2`, `_circle`, `_foo`, or Inkscape-generated garbage are equivalent. Preserve the original literal source IDs separately for diagnostics/reimport matching.
- [ ] Support independent normalized placement on both fretboard axes with tokens `ax<V>` and `ay<V>`, where `V` is in `[0,1]`. `ax` is longitudinal **nut -> bridge** within fret space `N` (between fret `N-1` and fret `N`); `ay` is lateral **treble -> bass** across the usable fretboard width. Omitted axes default to `0.5`, preserving the current centered behavior. Examples: `f12` = centered both axes, `f12_ax0` = nut-side aligned and laterally centered, `f12_ax1_ay0` = bridge-side + treble-side aligned, `f12_ax0.25_ay0.75` = normalized intermediate placement.
- [ ] Interpret `ax`/`ay` as **bounding/edge alignment of the complete logical inlay**, not as a point-coordinate for each child. First combine all geometry belonging to that semantic inlay into one logical group and determine its total plan-view bounds/usable motion range; then place the group as one unit. `ax=0` aligns the inlay's nut-side bound to the nut-side fret-space boundary, `ax=1` aligns its bridge-side bound to the bridge-side boundary, and intermediate values interpolate the available travel after subtracting the inlay extent. Apply the same principle laterally.
- [ ] Support optional signed millimetre padding directly on either alignment token: grammar `ax<V>[+/-mm]` and `ay<V>[+/-mm]`. The signed suffix is an **absolute physical offset in millimetres applied after normalized alignment**, not a change to the normalized value. Positive X is nut -> bridge and positive Y is treble -> bass. Therefore `ax0+2.5` means 2.5 mm inward from the nut-side fret boundary; `ax1-2.5` means 2.5 mm inward from the bridge-side boundary; `ay0+2.5` and `ay1-2.5` analogously mean 2.5 mm inward from the treble/bass edges. Intermediate forms such as `ax0.5+1` remain valid.
- [ ] Parse examples such as `f12_ax0+2.5_ay0.5_part1`, `f12_ax0+2.5_ay0.5_part2`, `f12_ax1-2.5_ay1-3_logo`, and `f7_ay0+1.5_dot` deterministically. Report malformed/contradictory semantic metadata in the existing Inlay SVG result table instead of silently falling back. Legacy `f<N>_...` IDs remain valid and mean centered placement (`ax=ay=0.5`) unless explicit axis tokens are present.

#### FreeCAD representation

- [ ] Create **one editable `Sketcher::SketchObject` per logical SVG inlay**, whether that inlay came from a tagged `<g>` or from multiple individually tagged elements sharing one semantic designation. Do not create one sketch merely per fret number or one sketch per SVG child. Preserve every child curve/loop as native Sketcher geometry where possible while retaining their relative positions inside the group. A multi-part logo/inlay therefore edits as one sketch and moves as one unit.
- [ ] Keep the sketch geometry in a stable **local inlay coordinate system**. Do not bake fret placement, normalized alignment or millimetre padding destructively into every control point. ## 6. Historical failures and lessons — do not repeat

1. The first neck refactor exposed generic `Part::FeaturePython` poles and `Part::Feature` cutters. This produced wrong generic icons, incomplete interactive editing and visibility/view-provider problems. Adding `.Proxy` to native `PartGui.ViewProviderPartExt` crashed in FreeCAD; use proper native feature types.
2. A heel plane was copied using a source face's identity `Placement`; the source geometry contained its world offset, so the new native plane ended up at the origin. Fixes must verify **world-space BREP**, not merely local Placement. FreeCAD quantities (`obj.Length`, `obj.Width`) must be compared via numeric `.Value` to unitless `BoundBox` floats.
3. Headstock fuse yielded an empty solid; repeated fuzzy-tolerance/repair attempts did not solve a wrong upstream geometry. Diagnostics showed the old and editable curve networks, Gordon surface, heel plane and trimmed blank became identical. **Fix the first divergent stage rather than add Boolean workarounds.**
4. The newer uploaded guitar exhibited an **inverted neck blank** (negative signed volume). Patch `0011` (`0.1.34`) corrects orientation before heel slicing; a focused test using saved BREP produced two heel-cut solids and a valid neck/headstock fusion. **This was not yet confirmed as passing in the user's full FreeCAD GUI** at handover.
5. The original March-era test document and newly reimported SVG document gave different results even on unmodified Marz master; imported shapes are persisted in the document and not necessarily recreated by **Update Parts**. Do not attribute every mismatch to Marz parameters or to the latest branch.
6. Mock and syntax tests did not catch runtime FreeCAD `Quantity` unit errors, missing view-provider properties or OCC errors. For future patches, prefer actual FreeCAD tests on the provided documents; record honestly when running FreeCAD is impossible.
7. The 0.1.36 SVG-to-Sketch pilot uses `Draft.make_sketch` on the *already transformed and anchored* native wire. A saved sketch overrides its legacy `Marz_*` source in existing consumers, but the terminal body/neck/headstock generators still write finished shapes, so **ordinary FreeCAD Recompute alone is not yet sufficient** to rebuild those assemblies; **Update Parts** consumes changed sketch geometry. Reimporting an SVG deletes only its corresponding editable sketches, intentionally discarding their edits. The menu conversion command does not overwrite a preexisting sketch. Version 0.1.62 supersedes the 0.1.44 single-spline contour representation: straight spans stay native lines and cubic spans stay exact B-spline segments, joined by Coincident constraints (requires explicit reimport for existing sketches).
